AI Quality Pilot 使用方法

以 deterministic engine 為核心，從環境確認、case 生成、測試執行，到 evidence、Knowledge Graph provenance、Task Graph 與 Gitea close-loop。這份頁面同時適用 Hermes 入口與直接 CLI。

快速導覽 1. 快速開始 2. 環境設定 3. Cases 4. Issues 5. Gitea PR Review 6. Graph Engineering 7. Close-loop 8. Wiki / Report 9. 狀態語意 10. 輸出位置

1. 快速開始

先選一種入口。Hermes 適合互動操作；CLI 適合 CI、scheduler 與本機除錯。兩者最後都呼叫同一套 deterministic core。

Hermes 入口

/quality-pilot
/quality-pilot setup
/quality-pilot doctor
/quality-pilot environment status

生產型命令會自動經過 grill-me 訪談與 write gate，不需要手動輸入 /grill-me。

直接 CLI

cd /root/repo/AI\ Quality\ Pilot
export PYTHONPATH=src
python3 -m quality_pilot.cli doctor \
  --root /path/to/product

若已安裝 package，也可以把前綴換成 quality-pilot。

auto_PID_tool 最短路徑

export PYTHONPATH=/root/repo/AI\ Quality\ Pilot/src
P=/root/repo/auto_PID_tool

python3 -m quality_pilot.cli setup --root "$P"
python3 -m quality_pilot.cli environment status --root "$P"
python3 -m quality_pilot.cli doctor --root "$P"
python3 -m quality_pilot.cli cases generate --root "$P" --init --count 5
python3 -m quality_pilot.cli cases review --root "$P"
python3 -m quality_pilot.cli cases validate --root "$P"
python3 -m quality_pilot.cli cases list --root "$P"
# 確認環境、fixture 與 marker 後，再執行單一 case
python3 -m quality_pilot.cli cases run --root "$P" <CASE_ID>
python3 -m quality_pilot.cli report status --root "$P"
不要直接執行裸的 cases generate。 必須明確指定 --init、--growing 或 --redmine-issues。

2. 環境設定與 TUI 探針

產品資料放在 host overlay；Quality Pilot 只保存環境設定與 redacted evidence，不保存 credential value。

確認環境

quality-pilot environment status --root /path/to/product
quality-pilot doctor --root /path/to/product

首次設定 local / remote profile

quality-pilot environment configure \
  --root /path/to/product \
  --mode local \
  --entrypoint 'python3 main.py --tui' \
  --fixture configs/config.yaml \
  --side-effect-boundary 'read-only sandbox; no production writes'

Remote profile 可另外指定 --target-host-env QUALITY_PILOT_TARGET_HOST；只保存環境變數名稱，不保存值。

執行 bounded PTY/TUI probe

quality-pilot environment tui-probe \
  --root /path/to/product \
  --duration 5 \
  --width 120 \
  --height 32 \
  --expect 'FAN ZONE STATUS' \
  --key enter \
  --confirm
  • 必須使用已確認的 environment profile。
  • --expect 是畫面 oracle；只看 process exit code 不算 PASS。
  • 缺 profile 或硬體前置條件：BLOCK
  • 未出現 expected marker：HOLD
  • 實際產品 workflow 與 BMC/IPMI 仍需產品專屬 adapter 驗證。

3. Cases：產生、檢查、執行

初始化

cases generate --init

第一次掃描 repo，產生 product-runtime contracts。

增長

cases generate --growing

依新 code、issue、PR、run 產生候選 cases。

Redmine

cases generate --redmine-issues 144780

從 Redmine MCP snapshot 產生 linked cases。

quality-pilot cases generate --root /path/to/product --init --count 5
quality-pilot cases review --root /path/to/product
quality-pilot cases validate --root /path/to/product
quality-pilot cases list --root /path/to/product
quality-pilot cases run --root /path/to/product CASE-001
quality-pilot cases run --root /path/to/product
quality-pilot cases push-pr --root /path/to/product CASE-001
執行規則： environment 未確認、fixture 不存在、remote target/credential 缺少或 entrypoint 不可用時，case 會回報 BLOCK，不會把錯誤包裝成 PASS。

4. Issues 與 Redmine/Gitea 同步

Issue sync 會處理 snapshot、dedupe、prune 與 local/remote mirror。Remote write 必須經 Hermes MCP 與 write gate。

# 讀取目前 MCP snapshot 並同步
quality-pilot issues sync --root /path/to/product

# 從指定 Redmine tickets 建立 linked handoff
quality-pilot issues sync --root /path/to/product \
  --redmine-issues 144780 144693

quality-pilot issues status --root /path/to/product
quality-pilot issues report --root /path/to/product
quality-pilot issues show --root /path/to/product 123

# 只產生本地 failure work item
quality-pilot issues create-from-failure \
  --root /path/to/product --local --case FAIL-001

# 準備遠端 Gitea issue handoff；不會繞過 gate
quality-pilot issues create-from-failure \
  --root /path/to/product --remote --case FAIL-001

--local 只寫本地報告；--remote 會產生 redacted MCP request，等待 Hermes 確認與套用。

quality-pilot issues fix --root /path/to/product --issue 123
quality-pilot issues fix --root /path/to/product --case FAIL-001
quality-pilot issues fix --root /path/to/product --issue 123 --push-pr

5. 任意 Gitea PR Review

Review 目標固定為 <owner/repo> + PR number，並釘住 detached branch head SHA。預設會先做 diff review、regression tests，以及透過 case generate/run 的 comprehensive QA matrix（black-box、white-box、functional、boundary、stress、documentation）；--dry-run 才只做計畫預覽，--diff-only 才跳過 comprehensive QA。

# 執行完整 local review + comprehensive QA，不產生遠端 write request
quality-pilot review pr \
  --root /path/to/product \
  --repo SmartFan/auto_PID_tool \
  --pr-number 27

# 只預覽計畫，不執行 case/tests
quality-pilot review pr \
  --root /path/to/product \
  --repo SmartFan/auto_PID_tool \
  --pr-number 27 \
  --dry-run

# comprehensive matrix PASS 後，才可明確確認並產生 gated request
quality-pilot review pr \
  --root /path/to/product \
  --repo SmartFan/auto_PID_tool \
  --pr-number 27 \
  --confirm

# Hermes MCP 套用後，reconcile result；不會重複發送第二次 write
quality-pilot review apply --root /path/to/product
沒有指定 PR 不會自動挑選。 目前 SmartFan/auto_PID_tool 有開放中的 PR，但請明確提供 PR number；此流程不會自行 merge。

Review gate

  • 必須有 deterministic test outcome 與 coverage。
  • stale head、failed report、duplicate result 會被拒絕或 HOLD。
  • Review 結果不能自行宣稱 APPROVED 或 MERGE_ALLOWED。
  • Gitea inline comments 只透過 gated MCP request 寫入。

6. Graph Engineering

Graph Engineering 有兩半：Knowledge Graph 描述 agent 記住什麼，Task Graph 描述 agent 如何工作。不需要 Neo4j 或遠端 database。

Knowledge Graph: scope → representation → ontology → extraction
                → quality-gate → fusion → evaluation → serving
Task Graph:     Context → Contract → parallel workers → verifier
                → merge → human gate → checkpoint → repair

Knowledge Graph

SQLite canonical、JSON export；優先從既有 case/run/evidence/review artifacts 建立 read model，entity/relation/event 都必須保留 source、confidence、時間與 evidence。

Ontology

先定義 competency questions、entity types、typed relations domain/range 與 event arguments，再接受 extraction candidates。

Task Graph

只有真實資料依賴才建立 edge；獨立 extraction 可平行，verifier 使用不同 owner/context。

Gate / Recovery

fusion 前需要 human gate；保存 checkpoint，失敗只修復 failed node 與 descendants。

quality-pilot graph tutor --root /path/to/product
quality-pilot graph scope --question "Which test run produced evidence?" --root /path/to/product
quality-pilot graph representation --root /path/to/product
quality-pilot graph ontology --root /path/to/product
quality-pilot graph run --from-qa --question "Which test run produced evidence?" --root /path/to/product
quality-pilot graph extract --input candidate.json --root /path/to/product  # external adapter
quality-pilot graph quality-gate --gold labels.json --root /path/to/product
quality-pilot graph fuse --root /path/to/product
quality-pilot graph evaluate --gold labels.json --root /path/to/product
quality-pilot graph serve --entity CASE-001 --root /path/to/product
quality-pilot graph run --from-qa --question "Which test run produced evidence?" --case-id CASE-001 --entity CASE-001 --root /path/to/product

Knowledge Graph 核心實作：src/quality_pilot/graph_engineering/；Task Graph 實作：src/quality_pilot/task_graph.py；BDD：docs/bdd/。Graph counts 不會成為 QA PASS。

quality-pilot close-loop run-once --root /path/to/product
quality-pilot close-loop run-once --resume-task-graph --confirm-publish --root /path/to/product
quality-pilot close-loop run-once --repair-node execute:CASE-001 --resume-task-graph --root /path/to/product
quality-pilot close-loop run-once --legacy --root /path/to/product

沒有 explicit confirmation 時 graph workflow 會在 fusion human gate 回 HOLD 並保存 checkpoint；confirmation 只允許 local graph merge，不會 remote write。

7. Close-loop 與排程

quality-pilot close-loop status --root /path/to/product
quality-pilot close-loop run-once --root /path/to/product --dry-run
quality-pilot close-loop run-once --root /path/to/product --case-id CASE-001
quality-pilot close-loop heartbeat --root /path/to/product --dry-run
quality-pilot close-loop heartbeat --root /path/to/product --every 12h --grow-count 20

heartbeat 只跑一次 tick，不會自行安裝 timer。Cron、CI 或 Hermes scheduler 必須負責下次觸發。

固定流程為：Observe → Normalize → Execute → Triage → Publish → Evolve → Prune。

9. 看懂輸出狀態

狀態意思下一步
PASS所有必要 oracle/evidence 都具備，且是 deterministic engine 判定。仍須依 workflow 的 write gate，不代表可直接 merge。
BLOCK前置條件缺失、環境未授權、credential/fixture/硬體不可用。先補前置條件；不要改寫成 FAIL。
HOLD有執行痕跡但 evidence 不足、marker 缺少或需要人工確認。補 evidence、確認 oracle 或重新執行。
candidateTask Graph/recommendation 的候選結果，不是 QA truth。回 source authority 再驗證。
SYNC_BLOCKED本地 deterministic workflow 可用，但遠端 MCP snapshot 或服務尚未就緒。先完成 snapshot handoff；不要進行 remote write。
安全底線： Task node 數量、process exit code、help/parser probe、空 issue 清單，都不能單獨證明產品 PASS 或 merge allowed。
